- ⛔ **PDFKit constraints, all guard-tested:** the PNG must be **8-bit, colour type 6
  (RGBA), non-interlaced** — PDFKit cannot embed an interlaced PNG and mishandles 16-bit
  depths, and the alpha is what lets chrome artwork sit on the white page with no plate
  behind it. ⛔ **Never quantise it to save bytes** — palette quantisation caps alpha at
  253 and the wordmark prints faintly translucent (the trap that already rejected a 9 KB
  email logo).
- ⛔⛔ **A MISSING LOGO FILE FAILS SILENTLY — `logoBuffer()` swallows the error by design
  ("Missing logo should never block invoice generation") and the PDF renders a text
  fallback with nothing in any log.** So a wrong filename produces a perfectly valid,
  logo-less invoice that nobody notices. The guard for that is behavioural, not a source
  match: PDFKit writes the embedded image's real pixel size into the XObject dict, so the
  test asserts `/Width 640` and `/Height 114` appear in the generated bytes of BOTH
  documents. **Any future logo change must keep that test honest by updating the
  dimensions it reads from the asset itself.**

  which starts at `mr - 170`), and the on-screen `.invoice-logo` went **160×44 → 196×35**
