- ✅ **The flow:** `GET /auth/google/start?next=` → Google's account chooser → `GET /auth/google/callback` (code → ID token; issuer/audience/expiry/`email_verified` checked) → the email is looked up in `User` → 302 to `/login?g=<60-second one-shot handoff>` → the portal takes `g` off the URL and POSTs `/auth/google/complete` → the ORDINARY login body. ⛔ **`/complete` hands the user to `completeLoginAfterPrimaryFactor` in `server.ts` — the SAME function `/auth/login` runs after bcrypt** (DISABLED → TOTP → sign-in code → session), so a person with the sign-in code on is still asked for it and the session body is byte-identical. `mfa.test.ts`'s wiring guard pins the password door onto it. **Never mint a session inside `googleLoginRoutes.ts`.**
- ⛔⛔ **NOTHING IS CREATED, EVER.** `decideGoogleLogin` = `not_registered` / `disabled` / `ok`. An unknown address bounces to `/login?google_error=not_registered` ("ask your administrator to add your email to your extension"). `INVITED` counts as registered (the create-a-password step becomes optional; the session path flips INVITED → ACTIVE as a password login already did). ⛔ **No 401 anywhere on this path** — a stale/replayed handoff answers **400**; a 401 stream from a login page auto-bans a customer's office at nginx.
- ⛔ **State + handoff tokens are HS256 on a key derived from `JWT_SECRET` under `connect:google-login:v1`** (the `mfa/preAuthToken.ts` fence) — no session verifier on the platform can accept them; the handoff carries only the user id and is single-use (`HandoffRegistry`). The ID token's signature is deliberately not verified (it arrives from Google's token endpoint over TLS in exchange for our client secret). The button is a plain `<a>` to the api — no Google script, no CSP change, no Turnstile token on that path.
