## 1. What existed before this session (found, not built — 2026-07-26 work)

Parts 1 and 2 of exactly this feature shipped on 2026-07-26 and sat dormant:

- **Part 1 — the per-user switch.** `User.smsEmailForwardEnabled` (migration
  `20260726130000`), toggled from Quick Controls
  (`ProfileMenu.tsx:456` "SMS to Email — Send my texts to my inbox"), served by
  `GET /voice/extensions/me/control-panel` + `PUT /voice/extensions/me/sms-to-email`
  (audited `SMS_TO_EMAIL_ENABLED/DISABLED`). **"People who have activated SMS to
  email" IS this flag — nothing else needs building on the opt-in side.**
- **Part 2 — the forward job.** `apps/agent/src/notify/smsEmailForwardJob.ts`
  polls fresh INBOUND `ConnectChatMessage` rows (`emailForwardedAt: null`,
  ≤30-min window — the backlog can structurally never be blast-emailed), emails
  every opted-in participant using the `smsEmail.ts` template (chat bubbles,
  dark-mode-safe, Outlook fallback), and stamps each row once.
- **One email thread per phone number was already the design**: every email for a
  chat thread carries `In-Reply-To`/`References` pinned to the synthetic root
  `<sms-thread-<threadId>@domain>` plus the STABLE subject `Text with <name>` —
  the subject stability is half the threading mechanism, do not "improve" it.
- **The signed reply address was already minted** (`sms+<threadId>.<sig>@replyDomain`,
  sig = first 24 b64url chars of HMAC-SHA256(JWT_SECRET, threadId)) — with **no
  verifier and no reader anywhere**. That was Part 3, and it is what this session
  built.

## 2. What this session built (Part 3 + hardening)

All in `apps/agent` (commit on `feat/ivr-migration-takeover`):

- **`notify/smsEmailReply.ts`** — the PURE rules: `mintSmsReplyAddress` (the
  forward job now calls this SHARED mint, so mint/verify can never drift — a
  test pins the output byte-identical to the historical inline format),
  `findSmsReplyAddress` (bound to OUR reply domain), `verifySmsReplySignature`
  (timing-safe), `isAutoGeneratedEmail` (OOO/bounce/list detection), and
  `extractSmsReplyText` (Gmail attribution incl. wrapped lines, Outlook
  dividers/From-blocks, `>` quotes, `-- ` signatures, "Sent from my iPhone";
  Yiddish/RTL passes through byte-for-byte; HTML fallback drops `gmail_quote`).
  ⛔ **The attribution join only spans CONSECUTIVE NON-EMPTY lines** — joining
  across a blank line made a message that *starts* with "On my way" vanish
  entirely (caught by the tests, would have been a silent reply-eater).
- **`notify/smsEmailReplyJob.ts`** — the decision layer. Per mailbox email:
  find + verify the signed address → drop auto-generated mail → load the thread →
  **match the From to an ACTIVE user of that tenant** → require the toggle ON and
  live thread participation → extract the words → **claim in `AgentAuditLog`
  (`sms.reply_claimed`, keyed on the email's Message-ID) BEFORE sending** →
  mint a **2-minute HS256 JWT for THAT user** (same claim shape as a login
  token) → `POST /chat/threads/:id/messages` on the real api.
  ⛔ **Reusing the real route is the design**: participant checks, the
  `can_send_sms` permission, outbound-number resolution, segmenting, MMS
  fallback and delivery tracking all stay in ONE implementation, and the reply
  is attributed in the app to the person — never to a robot.
- **`notify/smsImapSource.ts`** — thin IMAP adapter (imapflow + mailparser, new
  deps in `apps/agent/package.json`): UNSEEN search on INBOX, ≤20 per pass,
  hands parsed mail to the job, sets `\Seen` only on a handled mail. Gmail
  plus-addressing is what lets ONE mailbox serve every thread.
- **Wiring (`server.ts`, under the existing `AGENT_SMS_EMAIL=1` gate):** the
  bridge got its **own SMTP identity** (`AGENT_SMS_SMTP_*`, its own `Notifier`
  instance) — ⛔ deliberately NOT the shared agent notifier, so arming the
  bridge does not arm digests/incident mail, and the bridge sends AS the
  mailbox that receives the replies (DKIM alignment + reply routing both need
  that). Forward job's brand is now **"Loopcom"**. The reply job runs every 45 s
  only when the reply domain AND mailbox credentials exist.

## 3. Failure directions — chosen deliberately, tests pin each one

- **A stranger's From gets NOTHING back** — no text, no bounce, no oracle;
  refusal audited (`sms.reply_refused reason=unknown_sender`). Same for a user
  of a DIFFERENT tenant.
- **A known user who cannot send IS told** (toggle off, not a participant, empty
  reply, api refusal, api unreachable) — by a **threaded notice email** carrying
  the same `References` root and the same stable subject, with
  `Auto-Submitted: auto-replied` so their vacation responder never loops. They
  believe they just texted a customer; silence would be a lie.
- **A send is never auto-retried.** The claim is written before the POST; an
  unreachable api becomes an immediate notice + the mail marked processed. A
  duplicate text to a customer is worse than a failed one — the "purchase is
  never retried" rule.
- **Auto-generated mail is never texted** (Auto-Submitted, Precedence,
  X-Auto-Response-Suppress, null Return-Path, OOO/bounce subjects) — an
  out-of-office blurb texted to a customer is the classic bridge failure.
- **Spam to the bare mailbox is ignored quietly** — only mail addressed to a
  verified `sms+<threadId>.<sig>@` address is ever considered.

## 4. Arming it — the exact recipe (one human step, then ops)

**Izzy's step (nobody else can do it):** in the Google Workspace account
**sms@loopcom.net** — enable 2-Step Verification, then create an **App password**
(Google Account → Security → 2-Step Verification → App passwords). One 16-char
password covers both SMTP send and IMAP read. (Admin console must not have IMAP
disabled org-wide; default is enabled.)

**Then, in `/opt/connectcomms/env/.env.platform`** (agent reads it via env_file):

```
AGENT_SMS_EMAIL=1
AGENT_SMS_EMAIL_DOMAIN=loopcom.net
AGENT_SMS_EMAIL_REPLY_DOMAIN=loopcom.net
AGENT_SMS_SMTP_HOST=smtp.gmail.com
AGENT_SMS_SMTP_PORT=587
AGENT_SMS_SMTP_USER=sms@loopcom.net
AGENT_SMS_SMTP_PASS=<the app password>
AGENT_SMS_SMTP_FROM=Loopcom Texts <sms@loopcom.net>
```

(IMAP defaults itself: `imap.gmail.com:993` with the same user/pass;
`AGENT_SMS_IMAP_*` exist as overrides.)

**Then rebuild the agent** (it is in NO deploy queue — manual, and ⛔ reset the
server clone first, per [[agent-rebuild-needs-clone-reset]]):

```
cd /opt/connectcomms/app && git fetch origin feat/ivr-migration-takeover \
  && git reset --hard origin/feat/ivr-migration-takeover
docker compose -f docker-compose.app.yml -f docker-compose.agent.yml up -d --build agent
```

Verify in the CONTAINER, never the build log:
`docker exec app-agent-1 grep -c SmsEmailReplyJob /app/apps/agent/src/server.ts` → ≥1,
then boot audit rows `sms.email_enabled` AND `sms.reply_enabled` in `AgentAuditLog`.

⛔ **`SMS_PROVIDER_TEST_MODE`**: the worker's outbound SMS defaults to test mode

## 5. Acceptance test (10 minutes, needs a real phone)

1. Turn "SMS to Email" ON in Quick Controls for one user on a tenant with
   texting live (Loopcom Demo / inii mini / Create A Box).
2. Text that tenant's number from a personal phone → within ~1 min an email
   from **Loopcom Texts <sms@loopcom.net>** arrives, subject `Text with <you>`.
3. Text again → the second email lands **in the same Gmail conversation** (one
   thread per phone number — the whole ask).
4. **Reply** to the email with one line → within ~1 min the personal phone
   receives it as a text from the tenant's number, and the chat thread in the
   portal shows it as an OUTBOUND message from that user.
5. Negatives that matter: reply from a DIFFERENT mailbox (not a platform user)
   → nothing is sent, `sms.reply_refused` audited; an empty reply (just quoted
   text) → the "nothing was sent" notice email, threaded.

auto_generated / already_claimed).
