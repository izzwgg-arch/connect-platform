## 2. What this session built (Part 3 + hardening)

All in `apps/agent` (commit on `feat/ivr-migration-takeover`):

- **`notify/smsEmailReply.ts`** — the PURE rules: `mintSmsReplyAddress` (the
  forward job now calls this SHARED mint, so mint/verify can never drift — a
  test pins the output byte-identical to the historical inline format),
  `findSmsReplyAddress` (bound to OUR reply domain), `verifySmsReplySignature`
  (timing-safe), `isAutoGeneratedEmail` (OOO/bounce/list detection), and
  `extractSmsReplyText` (Gmail attribution incl. wrapped lines, Outlook
  dividers/From-blocks, `>` quotes, `-- ` signatures, "Sent from my iPhone";
  Yiddish/RTL passes through byte-for-byte; HTML fallback drops `gmail_quote`).
  ⛔ **The attribution join only spans CONSECUTIVE NON-EMPTY lines** — joining
  across a blank line made a message that *starts* with "On my way" vanish
  entirely (caught by the tests, would have been a silent reply-eater).
- **`notify/smsEmailReplyJob.ts`** — the decision layer. Per mailbox email:
  find + verify the signed address → drop auto-generated mail → load the thread →
  **match the From to an ACTIVE user of that tenant** → require the toggle ON and
  live thread participation → extract the words → **claim in `AgentAuditLog`
  (`sms.reply_claimed`, keyed on the email's Message-ID) BEFORE sending** →
  mint a **2-minute HS256 JWT for THAT user** (same claim shape as a login
  token) → `POST /chat/threads/:id/messages` on the real api.
  ⛔ **Reusing the real route is the design**: participant checks, the
  `can_send_sms` permission, outbound-number resolution, segmenting, MMS
  fallback and delivery tracking all stay in ONE implementation, and the reply
  is attributed in the app to the person — never to a robot.
- **`notify/smsImapSource.ts`** — thin IMAP adapter (imapflow + mailparser, new
  deps in `apps/agent/package.json`): UNSEEN search on INBOX, ≤20 per pass,
  hands parsed mail to the job, sets `\Seen` only on a handled mail. Gmail
  plus-addressing is what lets ONE mailbox serve every thread.
- **Wiring (`server.ts`, under the existing `AGENT_SMS_EMAIL=1` gate):** the
  bridge got its **own SMTP identity** (`AGENT_SMS_SMTP_*`, its own `Notifier`
  instance) — ⛔ deliberately NOT the shared agent notifier, so arming the
  bridge does not arm digests/incident mail, and the bridge sends AS the
  mailbox that receives the replies (DKIM alignment + reply routing both need
  that). Forward job's brand is now **"Loopcom"**. The reply job runs every 45 s
  only when the reply domain AND mailbox credentials exist.

## 3. Failure directions — chosen deliberately, tests pin each one

- **A stranger's From gets NOTHING back** — no text, no bounce, no oracle;
  refusal audited (`sms.reply_refused reason=unknown_sender`). Same for a user
  of a DIFFERENT tenant.
- **A known user who cannot send IS told** (toggle off, not a participant, empty
  reply, api refusal, api unreachable) — by a **threaded notice email** carrying
  the same `References` root and the same stable subject, with
  `Auto-Submitted: auto-replied` so their vacation responder never loops. They
  believe they just texted a customer; silence would be a lie.
- **A send is never auto-retried.** The claim is written before the POST; an
  unreachable api becomes an immediate notice + the mail marked processed. A
  duplicate text to a customer is worse than a failed one — the "purchase is
  never retried" rule.
- **Auto-generated mail is never texted** (Auto-Submitted, Precedence,
  X-Auto-Response-Suppress, null Return-Path, OOO/bounce subjects) — an
  out-of-office blurb texted to a customer is the classic bridge failure.
- **Spam to the bare mailbox is ignored quietly** — only mail addressed to a
  verified `sms+<threadId>.<sig>@` address is ever considered.

**The gate ladder (`smsEmailReplyJob.ts`), in order — all six must pass:**

1. a signed reply address is parseable from the To/Delivered-To
2. the signature verifies against the shared secret
3. not auto-generated / out-of-office
4. the thread exists and is type SMS
5. **the From is an ACTIVE `User` whose `tenantId` == the thread's tenant** ← *the one attempt died here*
6. that user has the toggle on, is still a participant, and the body is non-empty after quote-stripping

⛔ Step 5 is not merely a trust check. The job mints a **2-minute JWT for that
user** and drives the real `POST /chat/threads/:id/messages` **as them**, so the
outgoing text is attributed to a person, respects `can_send_sms`, and lands in
the CRM timeline under their name. There is no anonymous send path — an
unrecognised sender is *structurally* unsendable, not merely distrusted.

⚠️ One more silent-drop shape to know about: a mail client that replies to the
**From** (`sms@loopcom.net`) instead of the **Reply-To** loses the signed token
and is dropped at gate 1 as `no_reply_address` — indistinguishable from the junk
mail in the box. Most clients honour Reply-To (the one real attempt did), so
this has not bitten yet.

### §9.1 What was actually wrong

The signature was never the problem. On the 2026-08-20 drop it **verified, and it
resolved the thread** — the refusal row even carries `threadId`. It died at the
gate *after* that: the From address (`cgreenfeld@trustbookkeepingny.com`) matched

Meanwhile the thread row itself recorded exactly where that number routes:

```

```

**The system had the answer stored and threw the message away over the envelope.**

### §9.2 The rule now

**The sender comes from the thread's own SMS routing. The From header decides
nothing.** `ConnectChatThread.smsInboxOwnerUserId` → send as that person. No
owner → send with no name at all.

⛔ **`smsInboxOwnerUserId` is `''` (EMPTY STRING), not NULL, on a shared inbox.**
Measured: **301 owner-routed, 315 shared, of 616 live SMS threads.** An
`is not null` test reads all 315 as owned — it produced a wrong count in this
session before the join was redone. Truthiness is the correct test.

### §9.3 The guard rails (Izzy: *"as close to impossible as possible that there can never be any tenant leakage"*)

| Guard | Where | Measured today |
|---|---|---|
| Sender must be **ACTIVE** and in the **thread's own tenant** | `smsEmailReplyJob.ts` gate 3 | 0 cross-tenant, 0 inactive of 616 |
| Two different signed addresses ⇒ **refused, never resolved** | `findAllSmsReplyAddresses` | — |
| Failure notice only to **an address we hold**, never the From | `refuse()` | no oracle |
| **20 sends per thread per hour**, from the audit trail | gate 3 | survives restart |
| Every send records routed sender **and** the address that replied | `sms.reply_sent` | — |
| Nothing bypasses the real send path | route unchanged | participant + `can_send_sms` still server-side |

⛔ A reply is a **WRITE into one thread and nothing more.** Nothing about the
thread ever travels back to whoever replied.

### §9.4 The one new door, built as narrowly as possible

`POST /internal/chat/sms-system-reply` — **only** for shared inboxes.

- Takes **a thread id and a message and nothing else**. ⛔ **The tenant is derived
  FROM THE THREAD**; there is no tenant in the request to forge. That is the
  `inbound-crm-match` lesson (which read the caller's claimed role out of the body).
- **Refuses a thread that HAS an owner (409)** — it can never be used to strip
  attribution off an owned inbox.
- Registered in `jwtPublicRouteBypass.ts` **and** `internalSecret.test.ts`'s
  guarded list. ⛔ A missing bypass entry answers **401** and the door's own secret
  check never runs (403 = you reached the handler; 401 = you did not).

`sendConnectChatSmsMessage` gained `systemSender` beside `user`. ⛔ **Existing
callers are byte-identical**: participant + `can_send_sms` still run for a person,
and metadata still resolves to `undefined` when empty. Exactly one of
user/systemSender is required, checked up front.

**Proven live, all four directions:** outside → **403** at nginx; no secret →
**401**; wrong secret → **403**; owned thread → **409 with no send**.

### §9.8 Two testing traps this session walked into

1. ⛔ **The job marks a mail `\Seen` AFTER handling it.** A message you find
   already-seen was most likely **processed**, not skipped. This was misread as
   "Gmail auto-reads self-sent mail", the mail was re-fed, and the exactly-once
   claim correctly refused it (`already_claimed`, still exactly 1 outbound row) —

2. ⛔ **Do not wait on `event like 'sms.reply%'`** — it matches the pre-existing
   `sms.reply_enabled` row and returns instantly, so the wait exits before
   anything has happened and reads as "it did nothing".
