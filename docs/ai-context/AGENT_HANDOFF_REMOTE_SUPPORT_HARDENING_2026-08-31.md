## 2. ⛔⛔ THE TWO REAL BUGS. Both were invisible to a unit test.

### 2a. The second-arrival deadlock

A session flips to `ACTIVE` on the **first heartbeat from either side**. The
other side's `lastSeen*At` is still `null` at that instant, and the old rule read
`null` as *"gone silent"* rather than *"not here yet"* — so that side's very
first heartbeat was refused with `support_disconnected` **before it could ever
record one**.

**Whichever side arrived second could never join.** Which side that was came down
to a race between the customer's app and the technician's console, so it would
have presented as *"the support connection dropped"* immediately after consent,
on roughly half of all sessions, apparently at random.

⛔ The code's own comment already promised the grace period it did not deliver:
*"Between consent and the first beat there is a legitimate gap while the peer
connection is built."* That grace only held while the status was `CONSENTED`, and
the first beat destroyed it for the other party.

**The fix:** an absent heartbeat is measured against `startedAt` instead of being
treated as instant silence, so a side has the same window to **arrive** that it
has to go quiet. The ceiling is unchanged — nobody gets longer than
`HEARTBEAT_STALE_MS` — so a session still cannot outlive the banner showing it.

✅ **Proven non-vacuous:** 3 of the new policy tests fail replayed against the
pre-fix `policy.ts` and all 41 pass after.

### 2b. Body validation ran before the session lookup

`consent`, `signal`, `chat` and `request-capability` all parsed the request body
before loading the session, so the **shape** of a refusal differed depending on
whether an id existed. Existence now dominates on every session-scoped route —
the same ordering the desk-phone `authorize-reset` route was corrected to on
2026-08-21, for the same reason.

### 2c. And the NUL-byte trap, again

`events.ts` committed as `Bin 0 -> 10655 bytes`. Two **literal** control bytes
(`0x00`, `0x1f`) sat inside the filename sanitiser's character class where the
two-character escapes were intended. A source file git treats as binary has no
reviewable diff — on a file whose entire job is *"this can never record a
secret"*, that is the worst possible file to lose review on.

⛔ **The rule that catches it is already in CLAUDE.md and I still hit it:** check
`git show --stat` for `Bin` on any new source file. Also: **`sed -i` on source in
this repo injected a NUL byte** into `attack.test.ts`. Use the editor, or python
with explicit encoding — never `sed -i`.

## 4. ⛔ The rules that are now structural, and why each exists

1. **The kill switch never blocks stopping.** It gates request, consent,
   heartbeat, signal and input — and **never** `end`. A switch that could refuse
   `end` would, in the exact emergency it exists for, leave a live session
   running with no way to close it. A comment in the `end` handler says so.
2. **Off means the live session dies**, not merely that the next one is refused.
   Throwing the switch ends everything running in the same request. Proven at
   scale: 100 live sessions across 100 tenants, ended in 14 ms.
3. **State lives in the database, never a module variable.** This codebase has
   twice shipped state in a `Map` that re-armed on the next deploy. A deploy in
   the middle of an incident must not switch remote support back on.
4. ⛔ **A failed control READ fails CLOSED; a MISSING ROW means enabled.** These
   are opposite on purpose. No row means nobody ever touched the switch — the
   absence of a setting is a fact. A throw means we do not know whether someone
   is revoked, and not knowing must not be permissive.
5. **A capability needs both sides.** The technician asked AND the customer
   ticked AND the technician still holds the control key right now. Control does
   not imply clipboard; clipboard does not imply files.
6. ⛔ **`admin` is not in `REMOTE_CAPABILITIES` and its absence is the feature.**
   Elevated control needs a Windows service running as SYSTEM, which this version
   deliberately does not ship. Adding the string would not be sufficient — it
   needs its own local elevation prompt, audit event and technician role.
7. **A system event structurally cannot carry a secret.** The only free text in
   the whole surface is a chat line a human typed; every system sentence is
   composed from a closed vocabulary. Input is a **count**, clipboard is a
   **length**.
8. ⛔ **Remote support yields to phone calls, and only the CUSTOMER may say a call
   is up.** A technician claiming otherwise cannot buy bitrate back on someone
   else's machine. Proven by test.

## 5. ⛔⛔ THE PERMISSION RULE IS `null` AND MUST STAY THAT WAY

`{ prefix: "/remote-support", permission: null }` in `PORTAL_API_PERMISSION_RULES`.

**Gating it on `can_remote_support` would 403 every customer.** The person whose
screen it is holds no key — they are the one being helped — and `/pending`,
`/consent`, `/heartbeat`, `/signal`, `/chat` and `/end` are all called by them.
Same lesson as `/voice/diag` on 2026-08-24: a self-report surface gated on a
viewing permission silences exactly the people with the problem.

⛔ **And it cannot be narrowed by sub-prefix either.** `POST /remote-support/sessions`
is staff-only while `POST /remote-support/sessions/:id/consent` is the customer
answering, so any rule on `/remote-support/sessions` breaks consent. The split is
by **method and participant**, which a prefix cannot express. Authorisation is
per-route and per-participant in `policy.ts`, re-read live on every call.

The entry exists at all so the prefix **matches a rule** — without one the global
preHandler runs for nothing, which is the `/admin/wake-health` class, on the most
invasive capability on the platform. `/admin/remote-support` has its own entry
**and** `requireSuperAdmin` inside every handler.

⛔ The emergency routes are registered from **inside** `registerRemoteSupportRoutes`
rather than from `server.ts`. Two reasons: it needed no edit to a 40,000-line file
several sessions edit at once, and it guarantees there is no ordering in which
sessions can be started but not stopped.

**Attack suite — 42 tests through real Fastify.** Every one of these is refused:
cross-tenant session creation (and a foreign user id is **indistinguishable**
from a nonexistent one); a forged `tenantId`/`role`/`isSuperAdmin` in the body;
a stranger reading, beating, signalling, typing, chatting or ending someone
else's session; a colleague or a super admin consenting on the customer's behalf;

into a view-only session; a customer granting a capability nobody asked for; a
technician escalating mid-session; replaying a declined or ended session; and
~700 hostile bodies across 10 routes × 3 actors with **zero 500s**.

**Stress and soak — 13 tests.**

| | |
|---|---|
| 1 session, full lifecycle | 63 ms |
| 120 concurrent sessions | 1,233 ms · **97 sessions/sec** |

shape (nothing quadratic, no corruption, no leak), not a production figure.

⛔ **Two findings came from the stress test failing first, and both are kept in
the file.** A single-technician soak is **impossible**, correctly — 440 cycles

undrained signalling rows looked like a leak and was the *simulation* being
unrealistic; the real guard (age-based purge of an abandoned negotiation) is now
its own test.

**Suites:** 179/179 remoteSupport. Full apps/api **3,697 tests, 3,664 pass, 33
fail — all 33 pre-existing and documented** (24 `setupOrchestrator`, 7

# PART TWO — the screens, and three protections that were wired to nothing (2026-09-01)

## 9. ⛔⛔ THE HEADLINE: BUILDING THE UI IS WHAT PROVED THE SERVER RULES DEAD

Three protections were correct, unit-tested, deployed — and unreachable, because
nothing ever called them. Each is the same shape: **a CALLER-side omission**,
which a test of the policy, the route or the service passes straight through.

**(1) NON-NEGOTIABLE RULE 15 WAS ENFORCED AGAINST AN INPUT THAT NEVER ARRIVED.**
`decideMediaBudget` returns the small on-call budget the instant `callInProgress`
reads true. Grepping the whole portal for that field found it in exactly two
places — the service function's own signature and its return type. **Nobody set
it.** So "remote support yields to an active phone call" was a rule the system
could not act on, because nothing told it a call was happening.

⛔ Only the CUSTOMER's machine knows. The technician's browser cannot see the
customer's phone, and the server cannot either. It is supplied there now, from
`useOptionalSipPhone()` — ⛔ the *optional* hook, never `useSipPhone()`: this
component is mounted globally including outside the SIP provider, and chrome must
never crash the app over a missing provider.

⛔ Read through a **ref**, not a captured value. The peer's closure is built once,
when the session starts; the interesting case is a call that begins *later*.

**(2) THE ADAPTIVE BUDGET HAD NO NUMBERS.** `packetLoss >= 0.03 || rtt >= 300`
chooses the constrained budget. Neither was ever sent, so that branch could not
be reached. The peer now reads its own `getStats()` and carries the result.

⛔ **Loss is a DELTA between beats, never a lifetime ratio.** A lifetime figure is
dominated by the connection's first seconds and would keep reporting a bad link
long after it recovered — the encoder would stay clamped for the rest of the
session. ⛔ And a sample under 30 packets reports **nothing**: one lost packet out
of three is not 33% loss, it is noise, and acting on it clamps a healthy call.

**(3) THE MID-SESSION ASK REACHED NOBODY.** A technician could ask for the
clipboard or file transfer; the server recorded it; **the customer was never shown
the question.** `answerCapability` existed on the server and in the service layer
and was called by no screen at all. The rail would have sat on "Waiting for them
to answer…" forever, for a question that was never asked.

⛔ The ask is **derived**, never pushed: anything REQUESTED that is not yet
GRANTED is outstanding. A refresh, a reconnect or a second window all reach the
same answer, and a dropped message cannot lose it.

## 9a. ⛔ The guards read SOURCE, and all 15 fail against HEAD

## 10. What the screens do, and the decisions inside them

- **The rail draws tools from `granted`, never from `requested`.** Asking is a
  button; being allowed is a fact that arrives from the server. `requestCapability`
  deliberately returns `granted` unchanged so a screen *cannot* render a request
  as success.
- **Administrator windows are DRAWN as unavailable, not omitted.** Windows
  silently refuses injected input to elevated windows. A technician offered this
  would watch their clicks do nothing on a UAC prompt and conclude the product is
  broken. The server has no `admin` capability at all, so it cannot be granted.
- **The connection readout has a THIRD state.** Stats need two samples before loss
  means anything, so the first seconds legitimately know nothing — and a green
  light meaning "we have not looked yet" is exactly the reading somebody would
  trust while a customer struggles. It says *Measuring…*.
- **The customer is told WHY the picture softened.** Otherwise their screen share
  degrades the moment a call connects and they reasonably conclude that remote
  support broke their phone. It is the opposite: sharing stepped aside.
- **The capability question sits INSIDE the always-on-top banner, not a popup.**
  A popup can be behind another window, and a permission question nobody sees is
  one nobody can refuse. "No" is a real, equal button.
- **Chat renders as text.** The body is sanitised server-side; this is the second
  half of that promise. A transcript that interprets markup is one somebody can
  write into.
- **Activity is not filtered to "interesting" events.** The whole value of a
  record is that it is complete.

## 11. ⛔ The native-dropdown guard flagged its own explanation

The controls page used a native dropdown; the platform-wide sweep caught it and it
is a `ConnectSelect` now. The sweep **then flagged the comment explaining the
rule** — the sixth time this trap has been hit here.

⛔ **The guard was NOT weakened.** It drops only comment-shaped LINES and
deliberately has no block-stripper, because one opening a fake comment at a regex
literal would turn a negative assertion into a **false PASS**. The comment was
reworded instead. When a negative source guard flags correct code, fix the prose,
not the guard — unless the guard is genuinely wrong.
