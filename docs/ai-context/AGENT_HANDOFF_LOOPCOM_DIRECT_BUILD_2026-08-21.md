## §1 What it is, and why it is inert on the day it ships

A person types a phone number, finds the Loopcom user at another company, chats
with them, and starts a video call from the conversation.

⛔ **The whole feature is invisible until a person verifies their own mobile
number.** No `LoopcomDirectIdentity` row means they cannot be found, cannot be
messaged, and see a "verify to get started" card. So deploying this changes
nothing for any existing customer until somebody opts in — which is exactly the
rollout Izzy approved ("day one, nothing changes for anyone who does nothing").

## §2 The decisions, as built

Izzy said "build it like this" over a page carrying explicit recommendations, so
the recommended option was taken in each case. **If he meant otherwise, these are
the three switches to change:**

| Decision | Built as | Where |
|---|---|---|
| First contact | **B — message requests** (recommended) | `LoopcomDirectIdentity.requireRequests` default `true`; per-person toggle on the privacy screen |
| Identity | **verified personal mobile**, one-time SMS code | `LoopcomDirectIdentity.phoneE164` (`@unique`) |
| Rollout | **opt-in by verification** + per-company switch | `Tenant.loopcomDirectEnabled` default `true` (see below) |

⛔ **`loopcomDirectEnabled` defaults TRUE and that is deliberate, not an
oversight of the "every switch ships off" convention.** The real lock is
verification — with zero verified identities the feature is inert regardless —
and defaulting the tenant switch off would mean Izzy cannot try it without a DB
write. Setting it `false` for a company hides every one of its people from
search AND refuses their own verification.

## §3 The privacy rules — pure functions, one file

`apps/api/src/loopcomDirect/directPolicy.ts`. ⛔ The routes fetch rows and call
these; they never re-derive a rule inline. This is the one feature where company
A reaches company B, so the rules must be impossible to half-apply at one of
several call sites (the two-IVR-publish-paths defect shape).

- ⛔⛔ **NO ORACLE.** `decideLookup` returns the identical `{kind:"not_found"}`
  for four different truths: not on Loopcom, findable off, they blocked you, you
  blocked them, company switched off. A test asserts these are **deep-equal**,
  not merely all-not-found — an extra field on any one of them is the leak and
  would still pass a kind-only assertion.
- ⛔⛔ **THE ANTI-SPAM PROPERTY** is `decideCanSend`'s `awaiting_request` branch:
  while the other side has not accepted, the sender is capped at the ONE message
  they already sent. Without it "requests" delays spam by one tap.
- ⛔ **A pending request leaks no read receipt** (`visibleReadAtForOther`), and
  `POST /direct/threads/:id/read` refuses to record for a non-ACTIVE participant
  — so opening a request is safe, which is what the screen promises.
- ⛔ **Calling is strictly stronger than messaging** (`decideCanCall`): BOTH
  sides must be ACTIVE. A stranger must not be able to make a phone ring.
- ⛔ **Declining tells the sender nothing.** A test asserts the sender's own view
  contains no "declin*" signal anywhere.
- ⛔ `sanitizeMessageBody` strips control characters and bidi overrides (an RTL
  override renders a message as something other than what was sent) but **never
  spaces** — written as a code-point filter rather than a regex literal, because
  the escape form is easy to get wrong and a wrong one silently eats real text.
  (My own first draft did exactly that; the test caught it.)

## §4 Data model — deliberately NOT tenant-scoped

Migration `20260821180000_loopcom_direct` (generated by `prisma migrate diff`,
never hand-written; additive only — 6 tables, 2 enums, 1 boolean column with a
default).

⛔⛔ **There is no `tenantId` filter anywhere in `directRoutes.ts`, and a guard
test enforces that.** A Direct thread spans two tenants, so a tenant filter would
silently return nothing for every real conversation. Isolation is **per USER**:
every route resolves the caller's own participant row first, and a
non-participant gets 404 (the house convention — never 403, which is itself a
signal). **Every `ConnectChat*` model still carries its required `tenantId` and
none of that machinery was touched.**

`LoopcomDirectThread.pairKey` (sorted user ids, `@unique`) makes "one thread per
pair" a database guarantee rather than a query convention.

## §5 The video call — and what is honestly missing

`directCall.ts` creates a **`VideoMeeting` row** — the same table `/meetings`
uses, so a Direct call and a link-join meeting are the same machinery at
different sizes; there is no second video system to keep in step. It posts a
`CALL_EVENT` message carrying the join link into the thread and sends an ordinary
message push.

⛔⛔ **IT DOES NOT MAKE THE PHONE RING, ON PURPOSE.** `INCOMING_CALL` is the only
type the native Android service rings on, and borrowing it would make the phone
try to answer a SIP call that does not exist — actively broken. A proper
`INCOMING_VIDEO_CALL` type needs: `EXPO_PUSH_CALL_CONTROL_TYPES`, a branch in
`buildExpoPushV2Item`, both `callCriticalTypes` sets (api + worker), and a native
handler — i.e. **an app build**. That is Phase 3 and it is not done. What ships
works on every phone and browser today: tap the link, you are in the meeting.

⛔ The meeting row is created directly rather than through `POST /meetings`,
which is SUPER_ADMIN-only by Izzy's 2026-08-21 decision. That gate is about who
may HOST a room; a Direct call is a different door with its own rule (both people
already talking). Do not "fix" this by routing it through the SUPER_ADMIN door.

## §6 Light and dark — measured, not asserted

⛔ **Bare `:root` is DARK in this codebase; light is the opt-in override.** The
screen themes on `:root[data-theme="light"]`, never `prefers-color-scheme` (the
OS setting, which disagrees with the app's own toggle). A guard test enforces
that — ⛔ **and it must strip comments first**, because the file's doc block
explains why prefers-color-scheme is wrong and a naive `includes()` matches the
explanation. That trap has now bitten this repo five times.

⛔⛔ **INK vs FILL.** `--success`/`--warning`/`--danger`/`--accent` are DISPLAY
colours. Measured as TEXT on the light panel they are **2.28 / 2.15 / 3.76 /
3.68 : 1** — success and warning effectively unreadable. Text therefore uses
`--lcd-ink-*`, darkened for light only (**5.38 / 5.93 / 5.80 / 5.79 : 1**), while
fills, borders and dots keep the display colour. Verified live in a browser
against the real stylesheet: the "On Loopcom" pill computes `#0f7a4a` in light
and `#34c27b` in dark; the primary button `#3b82f6` vs `#22a8ff`.

## §8 The permission gate — the trap that would have shipped it ungated

⛔⛔ **`{ prefix: "/direct", permission: "can_view_workspace_chat" }` in
`PORTAL_API_PERMISSION_RULES` (server.ts) is what gates the whole surface.
Without that line a new prefix has NO permission check at all** — the
`/admin/wake-health` bug. A guard test pins it.

⛔ It reuses the **chat** key rather than a new one, following the Meetings
precedent: a new grantable key does NOT reach TENANT_ADMIN without a live
`PlatformRolePermissionSnapshot` refresh, so it would ship denying everybody.
The nav item and the page both gate on the same key, and the page supplies an
explicit `fallback` — a blank page reads as a broken app.

## §10 Acceptance (needs a human)

Two accounts in **different** tenants: verify a number on each → search the other
by number → the card shows their name and company with "On Loopcom" → send a
first message → **it lands in Requests, not the chat list** → the sender's second
message is refused → accept → both can talk → press the camera → both can open
the meeting link. **Then the negatives, which matter most:** search a number that
is not on Loopcom and confirm it reads exactly like a number whose owner has
blocked you; confirm a declined request tells the sender nothing; and confirm a
user with no verified number sees the verify card and nothing else.
