Design notes — Mobile Dashboard
The dashboard answers the three questions a mobile account owner actually has: is everything working (KPI row + line cards), is anything about to cost me money (attention list + next-invoice card), and what happened (activity rail). The attention list sits first because it is the only part that demands action; quick actions mirror the six most common support requests so they stop being tickets. The right rail is the money column — estimate, activity, charges — matching the Billing workspace's main-grid + right-rail pattern.

Design notes — Lines
The lines table is the product's center of gravity, so it carries the most state per row: lifecycle pill, SIM identity (masked ICCID — full value only behind the audited detail view), per-service state, usage-against-allowance bar, and the money column. Service chips are honest: Voice β and greyed SMS reflect the real carrier gates instead of pretending. Filters mirror every state the backend model has (draft/pending/active/suspended/lost/terminated + SIM type + origin).

Three cards, retail-only — wholesale cost and margin exist only in the owner console. Design notes — Porting
Porting is where mobile products lose trust, so the tracker is the hero: each request renders the same five-step stepper with the failure state inline and the fix one click away. The wizard collects exactly what wireless ports legally need (account #, PIN, matching name/address) and explains why in plain words. Submission to the carrier stays an owner-approved act — the customer's submit files the request with LoopCom, the console files it onward.
