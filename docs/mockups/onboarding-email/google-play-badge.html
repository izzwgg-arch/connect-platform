When the mail client blocks images

Outlook and some Gmail accounts hide images until the reader clicks “download pictures”. A badge is an image, so this is the state the button has to survive — the alt text becomes the link, and it still works. The old outlined button was live text, so this is the one thing the swap genuinely costs.

What this touches

  • Two emails, not one. Admin “invite user” and self-service sign-up both queue this same template through getAndroidApkUrlForInviteEmail(). The swap happens in the one template, so both paths move together — that shared resolver is exactly what stopped this link going missing on one path once before.
  • The badge has to be hosted by us. Mail clients can’t read a relative path or a data URI, and Google’s own CDN isn’t a reliable hotlink target. The asset ships to apps/portal/public/brand/google-play/ and the email points at an absolute https://app.loopcom.net/… URL, the same way the Loopcom wordmark already does.
  • The APK doesn’t disappear. /api/mobile/android/download and the portal Install page keep serving it. This is only about what the welcome email offers first.
  • iPhone stays out. The email has never had an iOS link and still won’t — the App Store build is in review, not published.
  • Guard test moves with it. androidApkInviteUrl.test.ts reads both call sites; it gets a case asserting the Play URL and badge markup are in the queued body, so a future edit can’t quietly drop it back to the APK.

Two things for you to call

I’ll build it either way you answer — these change the code, so I’d rather ask than guess.

01

Badge only, or badge plus a text line?

The images-off panel above is the tradeoff. Badge alone is the cleanest and matches Google’s guidelines; adding a small “Or open play.google.com/store/apps/details?id=…” line underneath means Outlook readers get a working link without clicking “download pictures”. Mocked as badge-only.

02

Hard-code the Play link, or make it an env override?

Today the URL comes from ANDROID_APK_DOWNLOAD_PAGE_URL if set, otherwise the APK page. Simplest is for the email to always point at the Play listing. Keeping the env override means one variable could swing every future invite back to the APK page — useful the day Play pulls a build, and a foot-gun the rest of the time.
